**NestNear — STAR Answer:** One of my key projects is **NestNear**, a PG and accommodation-finding platform that I developed to make it easier for students and users to find suitable accommodation based on **location, budget, and preferences**. **Situation:** The problem I wanted to solve was that traditional PG-finding platforms often show users a large list of properties, but finding properties that are actually close to a particular college, workplace, or location can be difficult. Simply searching by the name of an area is also not enough because two properties can be in the same general area but have very different distances from the user's actual location. **Task:** My task was to build a full-stack platform where users could search and filter PGs efficiently, especially based on geographic proximity, while also keeping the application architecture modular enough to support recommendation functionality. **Action:** I designed the application using a client-server architecture. The frontend was built using **React.js**, which handled the user interface, search forms, filters, property cards, and displaying results. The frontend communicates with the backend through HTTP requests rather than directly accessing the database. The backend was built using **Node.js**, and it acts as the main API and business-logic layer. For storing property information, I used **MongoDB**, because accommodation data is naturally document-oriented and can contain flexible fields such as property name, rent, address, room type, amenities, ratings, latitude, and longitude. The most important technical feature I implemented was **geospatial search**. Instead of storing a location only as text, I represented property locations using **GeoJSON Point objects**, containing longitude and latitude. I then used MongoDB's **2dsphere index**, which allows MongoDB to efficiently perform queries based on geographic distance. So, when a user searches for PGs around a particular location, the backend can work with coordinates and query MongoDB for properties within the required geographic area. This is more efficient than retrieving all properties and calculating distances manually in the application. I also separated the recommendation functionality using **Python and Flask**. The idea was to keep the recommendation or machine-learning logic separate from the React frontend and Node API. The Python service could process information such as location, preferences, or other accommodation attributes and return suitable recommendations through an API. The complete flow was therefore **user → React frontend → Node.js API → MongoDB**, with the Python-Flask recommendation component involved when recommendation processing was required. I also made sure the browser never directly accessed MongoDB because database credentials and database operations should remain on the server side. **Result:** The result was a functional full-stack accommodation platform with location-aware search and a modular recommendation architecture. More importantly, this project taught me how geospatial data actually works in a real application and why simply storing latitude and longitude is not enough. I learned how **GeoJSON and 2dsphere indexing** can make geographic search much more efficient, and I also learned the importance of separating presentation, business logic, persistence, and machine-learning responsibilities. If I were scaling the project further, I would add authentication and authorization, pagination, caching, image storage, monitoring for expensive geospatial queries, and potentially a dedicated recommendation service. So, NestNear gave me practical experience with **React, Node.js, MongoDB, REST APIs, GeoJSON, geospatial indexing, Python, Flask, and recommendation-system architecture**.


**The Gulmohar Digital Guest Assistant — STAR Answer:** My third project is **The Gulmohar Digital Guest Assistant**, a digital concierge application for a fictional boutique hotel called **The Gulmohar in Bengaluru**. **Situation:** The problem I wanted to solve was that hotel information is often scattered across different pages, FAQs, documents, and sections, while guests usually want quick answers to practical questions such as check-in and check-out timings, breakfast timings, room information, hotel facilities, policies, airport transfers, and other services. Instead of forcing guests to manually search through multiple pages, I wanted to provide a conversational hotel assistant. **Task:** My responsibility was to build a user-friendly hotel application and integrate a generative AI model so that users could ask questions naturally and receive answers based on the hotel's specific information. **Action:** I built the application using **Next.js, React, and TypeScript**. The frontend contains the hotel interface, login and registration screens, hotel information, and the conversational chat interface. I created a **structured TypeScript hotel knowledge base** containing information about rooms, facilities, timings, policies, and services. I intentionally used structured application data instead of introducing a full database because the hotel's information was relatively small and static for this project. The main AI component was **Gemini**, which I integrated using Google's **`@google/genai` SDK**. The basic flow is **user → Next.js chat interface → application logic → hotel context → Gemini API → generated response → chat interface**. When the user enters a question, the application captures the question and combines it with the relevant hotel context before sending it to Gemini. Gemini then generates a natural-language response, which is displayed back to the user. The important architectural idea was to separate **factual hotel information from language generation**. The knowledge base acts as the source of hotel-specific information, while Gemini is responsible for understanding the user's natural-language question and generating a conversational response. This also means that if the hotel changes something such as its breakfast timing or check-in policy, I can update the structured information without redesigning the entire application. I also handled the Gemini API key through environment configuration rather than exposing it directly in the frontend. Another major part of the project was testing. I used **Vitest** for automated tests and created scenario-based evaluations for different types of guest questions. During development, I encountered practical issues with the external Gemini API, including model compatibility and **429 free-tier rate limits**. Instead of allowing the entire test suite to depend on the live API, I mocked the model interaction for automated tests. This allowed me to test my application logic independently while using separate live tests for integration testing. **Result:** The result was an interactive digital hotel concierge that combined a domain-specific knowledge base with generative AI. The project gave me practical experience with integrating an external AI service into a real user-facing application rather than simply experimenting with a model in isolation. It also taught me about API failures, rate limits, testing external dependencies, environment variables, prompt/context design, and protecting API credentials. If I were turning this into a real production hotel system, I would add a backend service and database for dynamic information such as room availability, bookings, guest profiles, reservations, service requests, and payments. I would also make sure that Gemini could understand a user's request but could not directly modify sensitive database information. For example, if a guest asks for late checkout, the AI could understand the request, but a secure backend service should check availability and actually modify the reservation. This project therefore taught me not only how to integrate **Gemini, Next.js, TypeScript, and Streamlined AI workflows**, but also how to think about security and architecture when introducing generative AI into an application.

**Multi-Label Toxicity & Emotion Detection — STAR Answer:** Another important project I worked on is **Multi-Label Toxicity and Emotion Detection**, which is my machine-learning and NLP-focused project. **Situation:** The problem was to automatically detect different types of toxic content in text. This is particularly challenging because a single comment can contain multiple types of toxicity at the same time. For example, one comment could simultaneously be toxic, insulting, and threatening. Therefore, this is a **multi-label classification problem**, rather than a traditional single-label classification problem. I used a **10,000-sample stratified subset of the Jigsaw toxicity dataset** and worked with six toxicity labels. **Task:** My task was to build and evaluate an NLP classification pipeline, compare a traditional machine-learning approach with a transformer-based approach, improve performance on rare toxicity categories, and finally make the model usable through an interactive application. **Action:** I first created a baseline using **TF-IDF and Logistic Regression**. TF-IDF converts text into numerical features based on word importance, while Logistic Regression learns the relationship between those features and the toxicity labels. This baseline achieved a **macro-F1 of 0.49**. I then fine-tuned **DistilBERT using PyTorch**. I selected DistilBERT because it provides contextual language understanding while being lighter and faster than the full BERT model, making it more practical for an interactive application. The text first passes through the DistilBERT tokenizer, which converts the input into token IDs and attention masks. Those representations are then passed through the pretrained transformer, and I fine-tuned the model on the Jigsaw toxicity data. Because the problem is multi-label, the classification layer produces independent predictions for all six toxicity categories rather than forcing the model to select only one category. I compared the resulting model against my TF-IDF baseline and achieved a **macro-F1 improvement from 0.49 to 0.62**. I also achieved a **37% reduction in Hamming loss**, which measures incorrect individual label assignments across the multi-label predictions. I paid particular attention to rare categories because overall performance can hide poor performance on minority classes. The **threat F1 improved from 0.18 to 0.35**, **severe toxic improved from 0.29 to 0.46**, and **identity hate improved from 0.42 to 0.56**. I used macro-F1 rather than relying only on accuracy because macro-F1 gives each class equal importance, which is especially useful when the dataset is imbalanced. After the toxicity classifier, I added **zero-shot emotion detection using DistilRoBERTa**, allowing the application to analyze the emotional characteristics of text without requiring a separately trained classifier for every emotion. Finally, I built a **Streamlit application** around the models. The application takes user text, sends it through the toxicity classifier, produces the six toxicity predictions, and then uses the DistilRoBERTa component for emotion analysis. So the overall flow is **user text → Streamlit → preprocessing/tokenization → DistilBERT → six toxicity predictions → DistilRoBERTa → emotion predictions → results displayed to the user**. **Result:** The project successfully demonstrated that the transformer-based model substantially outperformed my traditional TF-IDF baseline, with macro-F1 increasing from **0.49 to 0.62**, while also improving performance on difficult rare classes. More importantly, I learned the complete machine-learning workflow rather than only model training. I learned how to formulate a multi-label problem, prepare an imbalanced dataset, create a baseline, fine-tune a transformer, select appropriate evaluation metrics, analyze per-class performance, integrate another transformer for zero-shot classification, and deploy the resulting models through Streamlit. If I were taking the project further, I would experiment with class-weighted or focal loss, independent thresholds for each toxicity label, hyperparameter tuning, larger datasets, model explainability, and a separate model-serving API instead of coupling the models directly to Streamlit. For a real moderation system, I would also include human review for sensitive decisions. Overall, this project strengthened my understanding of **NLP, PyTorch, transformer architectures, DistilBERT, DistilRoBERTa, multi-label classification, TF-IDF, Logistic Regression, macro-F1, Hamming loss, class imbalance, and model deployment**.
